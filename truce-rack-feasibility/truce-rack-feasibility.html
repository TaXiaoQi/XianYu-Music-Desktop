必须向决策层澄清的三件事：

  • “可行” 是打补丁后的可行。原版 CLAP 路径在加载任何遵守 CLAP 规范断言的插件时会直接 abort 进程；VST3 路径在销毁插件实例时必然触发访问违例。两者都已在本研究中修复并回归验证。
  • VST3 有一个运行时限制需要在宿主层规避：插件激活后 set_parameter 会被静默丢弃（详见 §5.3），播放器场景下可用“激活前设参 + 换曲重激活”策略完全规避，但实时调参面板的体验会受影响。

02背景、目标与边界

§课题来源

团队当前有两条并行的“插件”工作流：隔壁小组正在将前端插件引擎（MusicFree / LX / Baka 系 JS 音源插件）迁移至后端执行；本课题则研究后端音频 DSP 侧接入 VST3 / CLAP 这两类行业标准原生插件格式，为播放器引入专业音频效果生态（均衡、混响、动态处理、母带链等）铺路。

选型对象 truce-rack 是社区 Rust 插件宿主框架 rack 0.4.x 的重写版：纯 Rust 绑定原生插件 API（CLAP 走 clap-sys，VST3 走社区 vst3 crate，无需 Steinberg SDK 子模块与 CMake），默认启用 CLAP + VST3 双格式，MIT OR Apache-2.0 双许可[1]。此前调研已排除早期替代品 clack（v0.1.0，仅 CLAP，成熟度不足）。

§硬性边界（本次研究的约束）

Constraint · 不可影响移植组

前端插件引擎迁移是并行工作流。本研究只做只读分析与独立 PoC：不修改主工程任何文件；集成方案设计必须证明与移植组工作面零文件交集（见 §6.5）。

Constraint · 项目音频硬规则

工程已有两条既定约束必须在方案中继承：① Bit-perfect 输出开启时，PCM 必须绕过所有 DSP（仅保留解码器与安全限幅）——VST3/CLAP 机架同样必须旁路；② DSD 直出链路不经过 PCM DSP，本特性不涉及。

03验证方法与环境

§测试插件构建

本机此前未安装任何 VST3 / CLAP 插件，因此采用 nih-plug（社区广泛使用的 Rust 插件框架，同时是严格的宿主兼容性试金石）构建 gain 示例插件作为测试负载[3]：

  • gain 插件：线性增益参数，范围 −30 ~ +30 dB，幂律偏斜映射，50 ms 对数平滑——平滑特性要求验证套件必须等待过渡结束后再测量，否则会误判；
  • 一次构建同时产出 gain.vst3（目录式 bundle，内含 x86_64-win DLL）与 gain.clap（单文件 DLL）；
  • 安装至用户级扫描目录 %LOCALAPPDATA%\Programs\Common\VST3 与 ...\CLAP（无需管理员权限，也正是 truce-rack 在 Windows 上声明的用户级路径）。

§PoC harness 设计

独立 Rust 工程（truce-rack-poc，不进主工程），对每个发现的插件执行完整生命周期测试：

判定标准：稳态 RMS 输出/输入比应等于线性增益 0.5（±5%）；状态往返后参数值应精确还原；process 调用逐块计时评估实时余量；进程退出码必须为 0（teardown 无崩溃）。

Note · 参数值语义踩坑记录

两处容易踩坑的语义在本研究中被实测澄清：① VST3 与 CLAP 的参数值均为归一化 [0,1]（VST3 走 setParamNormalized，CLAP 规范本身即归一化），并非 truce-rack 文档声称的 "native units"——两格式语义其实一致；② nih-plug 的 Skewed 参数范围是幂律映射（plain = min + (max−min)·n^factor，factor≈5.03），线性增益 0.5 对应归一化值 0.4328，按对数映射估算会得到错误目标值。

05上游缺陷定位与补丁验证

原版 truce-rack 1.1.5（crates.io 与 git master 同源，最后提交 2026-06-19）存在两个进程级缺陷与两个需要宿主层规避的限制。本章给出根因、补丁与验证结果——这是本报告的核心增量：不仅回答“能不能用”，还回答“怎么修”。

§5.1 缺陷一：VST3 实例销毁必然崩溃（字段 drop 顺序错误）

现象：插件完成全部生命周期测试后，Vst3Plugin 被 drop 时进程以 STATUS_ACCESS_VIOLATION (0xC0000005) 崩溃。原版 harness 中 deactivate 成功但 drop 必炸。

根因：Rust 按结构体字段声明顺序 drop。Vst3Plugin 把持有 DLL 句柄的 _module 字段声明在 COM 指针字段之前，导致 DLL 先被卸载、随后 ComPtr<IComponent> 等 drop 时对已卸载代码调用 Release()——教科书级 use-after-unload。

Before · truce-rack-vst3/src/lib.rs
pub struct Vst3Plugin {
  info: PluginInfo,
  layouts: Vec<BusLayout>,
  active_layout: Option<BusLayout>,

  _module: LoadedModule,   // ← DLL 句柄在前
  component: ComPtr<IComponent>,
  processor: ComPtr<IAudioProcessor>,
  controller: ComPtr<IEditController>,
  // ... 其余字段
}
After · 一行字段重排
pub struct Vst3Plugin {
  info: PluginInfo,
  layouts: Vec<BusLayout>,
  active_layout: Option<BusLayout>,
  component: ComPtr<IComponent>,
  processor: ComPtr<IAudioProcessor>,
  controller: ComPtr<IEditController>,
  // ... 其余字段

  _module: LoadedModule,   // ← 移到末尾：DLL 最后卸载
}

验证：仅重排该字段（零逻辑改动）后，VST3 全生命周期含销毁均无崩溃，进程退出码 0。该补丁体量一行，vendor 成本可忽略。

§5.2 缺陷二：CLAP 加载时崩溃（向插件传 NULL 宿主指针）

现象：ClapScanner::load() 内部 create_plugin(factory, host, id) 调用后进程 abort（STATUS_STACK_BUFFER_OVERRUN，panic in non-unwinding FFI）。

根因：truce-rack 源码中赫然写着 let host = ptr::null(); // TODO(truce-rack): supply a real clap_host.——直接把空指针当作宿主传给插件。CLAP 规范要求宿主指针非空；nih-plug 在 Wrapper::new 中 assert!(!host_callback.is_null())，断言失败即 abort。任何遵守规范的插件都会触发此崩溃。

补丁：实现最小合法 clap_host 静态结构（约 40 行）：合法版本号、宿主名称字符串、get_extension 统一返回 NULL（不提供任何宿主扩展）、三个 request 回调为空操作。nih-plug 的 init 只查询 GUI / latency / params / voice-info / thread-check 五个扩展且对 NULL 返回均有优雅降级，最小宿主足够。

// truce-rack-clap/src/lib.rs —— 替换 `let host = ptr::null();`
static MINIMAL_HOST: clap_host = clap_host {
    clap_version: CLAP_VERSION,
    host_data: ptr::null_mut(),
    name: HOST_NAME.as_ptr().cast(),
    // vendor / url / version 同理，指向 C 字符串字面量
    get_extension: Some(host_get_extension),  // 统一返回 NULL
    request_restart: Some(host_request_restart), // 空操作
    request_process: Some(host_request_process),
    request_callback: Some(host_request_callback),
};
// load_from 中：
let host = &raw const MINIMAL_HOST;

验证：补丁后 CLAP 全生命周期通过：加载、参数显示（value_to_text 返回 "-6.02 dB"）、DSP ratio=0.5003、状态往返、销毁全部正常。该补丁也为后续接 GUI 扩展留好了挂点。

§5.3 限制一：VST3 激活后参数设置被静默丢弃

现象：激活后调用 set_parameter(gain, 0.4328) 返回 Ok，但读回仍是 0.5（默认值），DSP 输出无变化。

根因（双向夹击）：① truce-rack 的 VST3 wrapper 在 process() 中传 inputParameterChanges: null，完全不转发参数事件；② 其 set_parameter 走 IEditController::setParamNormalized，而 nih-plug 侧该函数在 is_processing == true 时静默 return kResultOk（符合 VST3 规范意图：处理中参数应走 process 队列）。truce-rack 的 activate() 即调 setProcessing(1)，因此激活后所有 set_parameter 全部无效。

宿主层规避（无需改库）：播放器没有 DAW 式自动化录制需求，参数集合在加载时即确定。策略：先设参后激活（本研究已验证有效）；用户改参数时缓存变更，在换曲/重新激活时应用（nih-plug 在 deactivate 周期保留状态，无音频断点之外的代价）。若未来要实时调参，需给 wrapper 补 inputParameterChanges 转发——工程量中等，属于“可等待上游 / 自行补”的增强项。

§5.4 限制二：Windows 默认扫描漏掉用户级目录

现象：default_vst3_paths() / default_clap_paths() 在 Windows 上读 HOME 环境变量拼用户级路径——而 Windows 标准 env 是 USERPROFILE，本机实测 HOME 未设置，默认 scan() 只能扫到 CommonProgramFiles 系统级目录。

宿主层规避：不依赖默认 scan，用 scan_path() 显式传入 %LOCALAPPDATA%\Programs\Common\{VST3,CLAP} 与 %CommonProgramFiles%\{VST3,CLAP}——一行配置的事，但若不知道这个坑会误判“用户插件扫不到”。

06集成架构方案

§6.1 现有音频管线与插入点

后端两条输出路径的 DSP 链已确认（共享模式 runtime.rs、独占模式 wasapi_exclusive.rs），插入点选在 SoundEffectSource 之后、UserVolumeSource 之前——与现有音效同级、位于主音量与限幅之前：

§6.2 逐样本 ↔ 块处理适配

现有 DSP 均为 rodio Source（逐样本迭代器），而 truce-rack 的 Plugin::process 是块级平面（planar）接口。适配方案与现有 SoundEffectSource 的帧缓冲模式同构：PluginHostSource 内部积累 512 帧交织输入 → 解交织为平面通道缓冲 → 组装 AudioBuffer（含 BusRange）→ 逐插件 process（机架串行）→ 交织回逐样本输出。缓冲粒度 512 帧 ≈ 10.7 ms @ 48 kHz，与 cpal 输出缓冲同量级，不增加可感知延迟。

§6.3 新模块划分（全部新建文件）

文件（src-tauri/src/player/plugin_host/）职责
mod.rs模块声明与对外类型
scanner.rs显式路径扫描（规避 §5.4），VST3+CLAP 聚合结果缓存
source.rsPluginHostSource：rodio Source 适配（块缓冲、交织/解交织、采样率与声道变化时 deactivate→re-activate、bit-perfect 旁路）

§6.4 关键运行时策略

  • 参数应用时机：加载/激活前一次性下发全部参数（§5.3 规避策略）；UI 修改入队，下次激活周期生效。
  • 状态持久化：save_state() 字节串以 base64 存入应用数据目录，随播放列表/设置同步体系走（与现有备份体系兼容）。
  • 采样率/声道切换：曲目间采样率不同时 deactivate → 按新采样率 activate（nih-plug 保留参数状态，已验证）。
  • 错误隔离：插件 process 返回 Error 时该块以静音穿透（fail-safe），并上报一次性 toast——第三方插件不可信，不能带崩播放线程。
  • GUI（二期）：插件自带编辑器窗口走独立原生 Win32 窗口（truce-rack 已有 PluginEditor 抽象与 Win32 句柄支持），规避 WebView2 airspace 遮挡问题；首期只做自绘参数面板。

§6.5 与移植组的零冲突证明

Impact Assessment · 对移植组工作面

文件交集 = 0。前端插件引擎迁移涉及 src/services（pluginManager、lxSearch、Baka 宿主逻辑）与 src-tauri/src/plugins.rs（脚本加载/账号同步）——全部在“音源插件”域；本方案落在 src-tauri/src/player/ 音频 DSP 域，新建 plugin_host/ 目录不与任何现存文件重名。

唯一触碰现有代码的位置：runtime.rs 与 wasapi_exclusive.rs 的 DSP 链组装处各新增一行包装（SoundEffectSource 之后插入 PluginHostSource），该处属于播放管线组装而非插件引擎，且可做成默认旁路的 opt-in 开关，合并顺序上完全解耦。

GUI airspace：WebView2 内嵌插件窗口遮挡问题 低（首期不做 GUI） 一期自绘参数面板；二期独立原生窗口承载插件编辑器

§7.2 分阶段路线

  • P0 · 无 GUI 宿主（建议立即启动）：vendor truce-rack + 合入双补丁；落地 plugin_host 模块（扫描/机架/参数面板自绘/状态持久化）；接入两条输出管线的 opt-in 插入点。验收口径即本报告 harness 的全部 PASS 项 + 真实第三方插件冒烟（建议拿 TDR Nova / Valhalla Supermassive 等免费插件实测）。
  • P1 · 原生窗口 GUI：PluginEditor → 独立 Win32 窗口；处理窗口生命周期与播放器窗口的 Z 序/模态关系。
  • P2 · 增强补齐：VST3 inputParameterChanges 转发（实时调参）、参数值显示、preset 浏览、多声道布局解析。

08结论与下一步

结论：后端接入 truce-rack 以支持 VST3 / CLAP 在技术上完全可行，且代价可控——双格式端到端 PoC 全部通过，性能余量三个数量级以上，两个崩溃级上游缺陷的根因与补丁均已定位验证（合计约 40 行修改），集成方案与移植组工作面零文件冲突。

决策建议一句话：以 vendor/fork 方式合入双补丁后按 P0 路线推进；不要直接依赖 crates.io 原版，也不要等待上游修复（活跃度不足）。

下一步行动清单：

  1. 将本研究验证过的两个补丁整理为 fork 提交（或 [patch.crates-io] 本地覆盖）；
  2. 在主工程新建 src-tauri/src/player/plugin_host/ 模块，按 §6.3 划分落地；
  3. runtime.rs / wasapi_exclusive.rs 两处 opt-in 插入点与移植组约定合并时序（建议晚于其引擎迁移主线，彻底错峰）；
  4. 引入 2–3 款真实免费插件做兼容性冒烟，建立崩溃插件黑名单机制。

本研究全部结论基于本机 PoC 实测（Windows 11 / Rust 1.97.1 / truce-rack 1.1.5 / nih-plug gain v0.1.0）；PoC harness、两个补丁源码与复现步骤已归档至本报告同目录 poc/（README 见 poc/README.md），可随时复查或复跑。
